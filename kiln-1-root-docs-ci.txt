# Kiln

A fast, secure, cross-platform Minecraft Java Edition launcher (Windows, macOS, Linux).
"Kiln" is a working codename: the display name lives in `kiln_core::APP_NAME` and
`src-tauri/tauri.conf.json`.

> Kiln is not affiliated with Mojang or Microsoft. Minecraft is a trademark of Mojang AB.
> A legitimately owned Minecraft account is required for online play.

**Status:** Phase 5 of 8 done (scaffold, settings, SQLite, logging, CI, Microsoft sign-in with OS keychain, version manifests, Java manager, verified downloader, launching, instances, Fabric/Quilt/NeoForge/Forge loaders, `.kiln.zip` and `.mrpack` import/export, Modrinth browsing, installs with dependencies, updates with automatic rollback, modpack install and update). Real sign-in needs an approved client ID: see [docs/AUTH.md](docs/AUTH.md). Real downloads, loader installs, launches and Modrinth traffic have only been tested against mock servers. See
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for the roadmap.

## Layout

| Path | Purpose |
|---|---|
| `crates/kiln-core` | All launcher logic. No GUI dependency, fully unit-tested. |
| `src-tauri` | Tauri 2 shell: validates IPC input, calls core, maps errors. |
| `ui` | Svelte 5 + TypeScript + Tailwind 4 frontend. |

## Build and test

Requirements: Rust 1.85+, Node 22+. On Linux, Tauri's system libraries
(`libwebkit2gtk-4.1-dev`, `libgtk-3-dev`, `libayatana-appindicator3-dev`, `librsvg2-dev`,
`libsoup-3.0-dev`) plus `libdbus-1-dev` for the keychain.

```sh
# Core logic only (no WebView libraries needed)
cargo test

# Whole workspace, as CI runs it
(cd ui && npm ci && npm run build)
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace

# UI checks
(cd ui && npm run check && npm test)

# Run the desktop app
cargo install tauri-cli --version "^2" --locked
cargo tauri dev
```

`npm run dev` inside `ui/` also works in a plain browser using an in-memory stand-in for
the backend, which is handy for styling work. Set `KILN_LOG=debug` (any `tracing` filter)
to override the log level.

## Data and portable mode

Data lives in the platform data directory under `Kiln`. Create a file or folder named
`kiln-portable` next to the executable to keep everything in `kiln-data/` beside the app.

## Security model (summary)

Full document arrives in Phase 8. What already holds:

- Only the `allow-*` permissions in `src-tauri/capabilities` are granted to the webview;
  there are no `fs`, `shell` or `http` plugins.
- Strict CSP: no inline or remote scripts, no `eval`, fonts and styles from the app only.
- Every log line passes through a redactor that masks tokens, launch credentials,
  e-mail addresses and OS account names before it is written.
- `SafePath` is the only way to turn untrusted relative paths into file operations: it
  rejects `..`, absolute paths, Windows device names and symlink escapes.
- Sign-in tokens: refresh tokens exist only in the OS keychain, access tokens only in memory, and
  none ever reaches the webview or a log.
- All network traffic goes through one client that is HTTPS-only, allowlisted by host and
  never follows redirects.
- Hashes are verified with SHA-1/256/512 before any downloaded file is kept (files are written to `.part` and renamed only after verification).
- Archives are extracted through `SafePath` (zip-slip safe), with hard links refused, symlinks confined to the target folder and a size cap.
- Game output shown in the Console passes through the log redactor first.
- Per-instance Java arguments are vetted (no agents, no `-XX:OnError`, no overriding Java's own paths); imported packs never bring JVM arguments, and nothing in a pack is executed.
- The webview never supplies a file path: imports name a file in Kiln's `imports/` folder, exports go to `exports/`.
- Forge and NeoForge installers run their processors with the user's privileges, after the installer's published checksum is verified: see `docs/NEXT_STEPS.md` for the trust note.
- Mods: ids are validated before they reach a URL, a file is installed only if its name is a plain `.jar`, its URL is on `cdn.modrinth.com` and it carries a hash that matches after download. Jars Modrinth doesn't know are labelled "Unverified" and never show an author, download count or licence. An update keeps the old jar; if the game then fails to start within two minutes, Kiln checks the backup against its recorded hash and puts it back. Modrinth's rate limit is honoured and API responses are cached by ETag. Modpack updates never overwrite or remove files you added.
- No telemetry.

## Licensing

Kiln is released under **GPL-3.0-only** (see `LICENSE`). Bundled or auto-installed mods
keep their own licenses; Kiln only downloads them from their official source and never
redistributes them itself. A Modrinth `.mrpack` export lists mods Modrinth hosts by hash and URL
instead of copying them; jars Modrinth doesn't know are bundled, and Kiln lists them so you can
check you may share them.

# Architecture

Approved design for Kiln. Boundary rule: `ui -> IPC -> src-tauri -> kiln-core`; all
logic and tests live in `kiln-core`.

## Modules in `kiln-core`

Implemented: `paths` (data dirs, portable mode, `SafePath`), `hash`, `redact`, `logging`,
`db` (SQLite, WAL, migrations), `settings`, `error`, `net` (allowlisted HTTPS client, streaming
GET with per-hop redirect checks), `auth` (device-code sign-in, keychain, accounts), `download`
(parallel, resumable, hash-verified, atomic `.part` rename), `archive` (zip and tar.gz, zip-slip
safe), `mojang` (version manifest, version JSON, `rules`, libraries, natives, asset index, profile merging), `java`
(detect installed JDKs, download Temurin), `launch` (argument building, pipeline, one-game manager,
events), `loader` (Fabric and Quilt profiles from their meta APIs; Forge and NeoForge through their
official installers), `instance` (instance store, JVM-argument vetting, `.kiln.zip` and `.mrpack`
import/export).

`mods` (Phase 5):
- `source.rs`: the `ModSource` trait and catalogue-neutral types. Ids are validated (`[A-Za-z0-9_-]`,
  at most 64 chars) before they go into a URL; file names must be plain `.jar`s.
- `modrinth.rs`: the Modrinth v2 implementation. Host allowlist `api.modrinth.com` for the API and
  `cdn.modrinth.com` for files (`ModSource::download_policy`, checked again for every file URL before
  a download is queued). User-Agent is `Kiln/<version> (<contact>)` (`mods::CONTACT`). GET responses
  are cached with their ETag in `http_cache` (keyed by a hash of the URL; bodies in `cache/http/`)
  and reused without a request for five minutes. Rate-limit headers and 429s are honoured: short
  waits are slept off, long ones fail with a "try again in N seconds" message.
- `store.rs`: the `mods` table, scanning `mods/` (size and mtime skip re-hashing; symlinks are
  ignored), pin, enable (`.jar.disabled`), remove, update backups (`mod_backups`, files under
  `backups/mods/`) and rollback. No network code, so the launch manager can use it.
- `service.rs`: dependency resolution (required, optional offered, incompatible blocks), install,
  update scan by SHA-1 (`version_files/update`), update, update-all, modpack install and update,
  `.mrpack` export with Modrinth hashes.

Rollback: an update records the replaced jar (copied before anything is written) as `pending`. When
the game exits abnormally within two minutes of starting, `LaunchManager` calls
`ModStore::rollback_pending`, which checks each backup against the hash recorded before the update,
puts it back and removes jars the update added. A clean exit, or a run longer than the window,
confirms the update; stopping the game yourself decides nothing.

Planned: `perf`, `crash`, `backup`, `servers`.

Implemented: `get_app_info`, `get_settings`, `set_setting`, `auth_begin_device_flow`,

`auth_cancel`, `auth_open_verification_page` (takes no argument: the address comes from the

Instances and the version picker: `picker_game_versions`, `picker_loader_versions` (only versions the
chosen loader supports), `instance_list`, `instance_create`, `instance_rename`, `instance_clone`,
`instance_delete`, `instance_update_settings`, `instance_export`, `instance_list_imports`,
`instance_import`, `open_folder`. None takes a file path.
Launching: `launch_start` (takes only an instance id; the account, settings and Java come from the
backend), `launch_stop`, `launch_status`, `launch_log`. Progress and output reach the UI

capability file grants `core:event:allow-listen` and `allow-unlisten` for them.
Mods: `mod_search`, `mod_project`, `mod_versions`, `mods_list`, `mod_install_plan`, `mod_install`,
`mods_check_updates`, `mod_update`, `mods_update_all`, `mod_set_pinned`, `mod_set_enabled`,

which jars were bundled. Long operations report through the `task-progress` event (counts only); an
automatic rollback is announced with `mods-rolled-back`. One mod operation runs at a time, and none
runs on an instance whose game is starting or running (and the game won't start during one).
Skin and cape URLs are part of `Account`, so there is no separate `auth_get_skin`. Every command must be listed
in `src-tauri/build.rs` and granted in `src-tauri/capabilities/default.json`.
Errors cross the boundary as `{ code, message }` with a plain-English message.

# Microsoft sign-in

## How it works

Kiln uses Microsoft's **device-code flow**: the app shows a short code, the user enters it
on microsoft.com in any browser, and Kiln polls until they finish. There is no embedded
webview, no local redirect server, and Kiln never sees the user's password.

```
Microsoft device code -> MS access + refresh token
  -> Xbox Live user token -> XSTS token (relying party rp://api.minecraftservices.com/)
  -> Minecraft access token -> Minecraft profile (404 means the account doesn't own the game)
```

Where things live:

| Item | Storage |
|---|---|
| Refresh token | OS keychain only (Credential Manager / Keychain / Secret Service), stored as raw bytes |
| Minecraft access token | Memory only, wiped on drop, refreshed ~5 minutes before expiry |
| Device code | Memory only, never sent to the UI |
| Account name, skin hash, flags | SQLite (`accounts` table), no secrets |

No token ever crosses the IPC boundary. The UI receives `Account` and `DeviceCodeInfo`; only the
launch pipeline can ask the backend for a `LaunchSession`.

## Setup you must do before real sign-in works

1. **Azure app registration** (portal.azure.com, App registrations, New registration).
   - Supported account types: personal Microsoft accounts (consumer accounts).
   - Name: must not contain "Mojang", "Minecraft" or similar protected words.
   - Redirect URI: leave empty (device flow doesn't use one).
   - Authentication, Advanced settings: **Allow public client flows = Yes**. Without this Microsoft
     returns `AADSTS70002`.
   - No client secret. Copy the **Application (client) ID**, a GUID.
2. **Ask Mojang to approve the client ID** at <https://aka.ms/mce-reviewappid>. Until then
   `login_with_xbox` answers 403 "Invalid app registration" and Kiln shows
   "Mojang hasn't approved this build's Microsoft app registration". Reviews have been reported as
   weekly; the form is authoritative, not this document.
3. **Give the ID to Kiln**, either:
   - at runtime: `KILN_MS_CLIENT_ID=<guid> cargo tauri dev` (handy while testing), or
   - at build time: set `KILN_MS_CLIENT_ID` in the environment when building releases (it is read
     with `option_env!`). A client ID is public information, not a secret.

Anything that isn't a well-formed GUID is treated as "not configured".

These steps were checked against third-party documentation and a Microsoft Q&A thread, not
Mojang's own pages. Verify against the form before relying on them.

## Errors users can see

| Situation | Message gist |
|---|---|
| No client ID in this build | Sign-in isn't set up in this build |
| Code not used in time | The code expired, start again |
| Declined on Microsoft's page | Sign-in was cancelled |
| XSTS `2148916233` | No Xbox profile yet; sign in at xbox.com once |
| XSTS `2148916235` | Xbox unavailable in the account's region |
| XSTS `2148916236` / `2148916237` | Adult verification needed |
| XSTS `2148916238` | Child account; an adult must add it to a family group |
| Profile 404 | Account doesn't own Minecraft: Java Edition |
| Refresh rejected, or keychain entry missing | Sign in again (account stays listed, flagged) |
| Keychain unavailable | Explains how to unlock it; nothing is stored in plaintext as a fallback |

## Platform notes

- **Linux** needs a running Secret Service provider (GNOME Keyring or KWallet), unlocked.
- **Windows** Credential Manager limits a blob to 2,560 bytes. Tokens are stored as raw UTF-8 bytes
  (the string API would store UTF-16 and double the size). A real refresh token is ~1.5 KB.

## Testing

Everything except the real OS keychain is covered by unit tests against a mock server
(`cargo test`). The keychain test is ignored by default because most CI machines have no unlocked
keychain: run `cargo test -p kiln-core -- --ignored keyring` on a machine that has one.
It has been run on Linux with GNOME Keyring; macOS and Windows are untested.

## Rules the codebase already follows (keep them)

- All logic and tests live in `crates/kiln-core`; `src-tauri` only validates input, calls core and
  maps errors. Strict clippy: `unwrap_used`/`expect_used` are denied outside tests.
- Untrusted relative paths go through `paths::SafePath`/`validate_relative`. Never build file
  paths from archive entries, modpack manifests or IPC strings any other way.
- All network traffic goes through `net::HttpClient`: HTTPS only, per-client host allowlist, no
  redirect following, 2 MiB response cap, never logs URLs beyond host and path or any body.
  Redirect-following for downloads must re-check every hop against the allowlist.
- Secrets: refresh tokens only in the OS keychain; access tokens in `SecretString` (hidden from
  `Debug`, zeroized, auto-registered with the log redactor); no token crosses IPC or reaches a log.
  Never add a plaintext fallback.
- Every IPC command must be listed in `src-tauri/build.rs` `COMMANDS` **and** granted in
  `src-tauri/capabilities/default.json` (`allow-<kebab-name>`), and return `Result<T, AppError>`
  with a plain-English message. Validate inputs in the command (see `commands/auth.rs`).
- Strict CSP in `tauri.conf.json` (no inline scripts/styles, fonts self-hosted, `img-src` allows
  only Modrinth CDN and `textures.minecraft.net`). Avoid Svelte transitions (they inject `<style>`);
  use CSS transitions.
- Legal: no cracked/offline-auth features, no Minecraft logos or assets, state non-affiliation
  with Mojang/Microsoft, respect mod licences.
- No telemetry. No background polling when idle.
- Design language: "glaze" palette (celadon accent on slate-green dark; green-grey paper light),
  Bricolage Grotesque headings and Public Sans body, ruled rows instead of card grids, user-themeable
  accent. Follow the existing tokens in `ui/src/app.css`.
- Downloads: every destination is a `SafePath`; files reach their final path only after hash
  verification (`.part` then rename). Archives are extracted only through `archive::*`. Loader and
  pack downloads use their own host allowlists (`loader::host_policy`, `instance::pack::mrpack_policy`).
- The webview never supplies a file path. Imports name a file in the `imports/` folder, exports go to
  `exports/`, `open_folder` takes a fixed choice. Do not add a dialog or fs plugin.
- User-supplied JVM arguments go through `instance::parse_jvm_args`; values from packs or other
  untrusted sources are dropped, not trusted.
- The UI never receives a token, a URL with credentials, or an unredacted game log line.

### Phase 4

- Real Fabric, Quilt, Forge, NeoForge and Modrinth-CDN traffic has never run. Loader installs, the
  Forge/NeoForge installer pipeline and `.mrpack` downloads are verified against wiremock and a fake
  `java` script only. **A real Forge or NeoForge install has never happened**; expect surprises in
  real installer profiles (library `url: ""` entries, `data` entries, processor argument forms).
- Loaders install lazily on first launch (profile saved under `cache/loaders/`, libraries shared in
  `cache/libraries`), not when the instance is created. Fabric/Quilt libraries get their SHA-1 from the
  `.sha1` file next to each artifact on the same Maven host, which protects against corruption and bad
  mirrors, not a compromised repository. The Forge/NeoForge installer is checked the same way, and its
  processors run as Java programs with the user's privileges; each processor's declared output hashes
  are verified.
- Supported ranges: Forge from Minecraft 1.17 (older installers use a different format), NeoForge
  `20.x`-`25.x` version numbers (the new year-based Minecraft numbering is not mapped). The picker hides
  everything else. Library URLs in loader profiles must be on the loader allowlist
  (`loader::host_policy`) or the download is refused.
- Packs: `.mrpack` import honours `env.client`, requires a checksum (sha512 preferred), accepts only the
  spec's hosts (plus GitHub's CDN), applies `overrides/` then `client-overrides/`, and never runs
  anything. `.mrpack` export leaves out worlds and (since Phase 5) lists Modrinth-hosted mods by hash and
  URL, bundling only other files; `.kiln.zip` export includes worlds. Imported JVM arguments and Java
  choice are dropped; only RAM is kept. Import progress reaches the UI (Phase 5, `task-progress`).
- The webview never supplies paths: imports name a file in `imports/`, exports land in `exports/`,
  `open_folder` accepts a fixed set. There is no native file dialog by design (no dialog plugin).
- `LaunchRequest` now carries the instance (version, loader, folder, RAM, vetted JVM flags, optional
  Java path); `launch_start` takes an instance id. Play time is recorded when a game that reached
  "running" exits. The Console no longer has a version picker. The per-instance Java runtime
  (`java_id`) is supported by the backend but has no UI yet. The `mods` table is populated by `ModStore::sync` (Phase 5).
- Mutation checks done for Phase 4 (each applied, each caught): JVM deny-list, deleting a running
  instance, reserved `.kiln*` paths in `.mrpack`, `.mrpack` host filtering, `.mrpack` hash
  verification, reserved paths in native packs, library hash verification, Forge processor output
  verification, installer checksum verification, confinement of Maven coordinates to the libraries

- Detached builds die if the call that starts them also does other work. Start them alone

### Phase 5

Everything is verified against a fake Modrinth (`mods::testkit`) only: real Modrinth traffic has never
run, and whether Modrinth sends ETags is unconfirmed (the cache works without them: it then re-fetches
after the 5-minute TTL).

- Updates are found by hashing installed jars (`version_files/update`, SHA-1). Dependencies of a new
  version that aren't installed are installed too and recorded so a rollback removes them. A failed
  batch removes the files it created and a failed update puts the old jar back (found by tests: files
  download side by side, so another file's failure can leave one behind).
- Rollback heuristic: exit code not 0 within `STARTUP_WINDOW` of the game reaching "running" undoes
  every pending update for that instance; a clean exit or a longer run confirms them; pressing Stop
  decides nothing. Backups are hash-checked before restoring. Confirmed backups are pruned to 20 per
  instance. The launch-hook tests are Unix-only. Windows exit-code behaviour is untested.
- `mod_versions` can exceed the 2 MiB response cap for projects with very many versions (it then fails
  with a plain error). Search and install always filter by loader and Minecraft version.
- `.mrpack` export needs the network (it asks Modrinth for each mod's hashes and URL) and fails offline
  on purpose rather than silently bundling mods. Jars Modrinth doesn't know are bundled and reported
  (`bundled_unverified`) so the person can check they may share them.
- Modpack update: files the old pack put there and the new one doesn't are removed (copied to
  `backups/packs/<instance>/<time>/`); files the person added are never overwritten or removed;
  `saves`, `options.txt`, `servers.dat`, `screenshots`, `logs`, `crash-reports` are never touched.
  Pack-owned files are recorded in `instance_packs.files`.
- Mod operations on an instance are refused while its game is starting or running; `launch_start` is
  refused while a mod operation holds `AppState::mod_ops`.
- Mutation checks done for Phase 5 (each applied, each caught by a test): id validation, the file-URL
  host allowlist, download hash verification, rollback's backup hash check, 429 handling, `If-None-Match`,
  the pin check, modpack-update protection of user files, optional-dependency validation, the cache
  body-path check, symlinked jars, the response header filter, the launch rollback hook, cleanup after a
  failed batch, the jar-name check, restoring the old jar after a failed update. The real binary under
  Xvfb rendered the Mods screen, showed plain errors offline, and a removed capability grant broke it.
- `npm audit --audit-level=high` fails since the advisory database updated on 2026-11-17: picomatch
  (ReDoS through crafted glob patterns, GHSA-fc5q-39xc-vjpf) has no patched release (4.0.7 is the
  newest and is flagged), and it is pulled in by vite, vitest and svelte-check. It is a build-time
  tool: `npm audit --omit=dev --audit-level=high` passes and the built `ui/dist` contains no picomatch.
  npm's suggested fix is a breaking downgrade of vite, so nothing was changed. CI's audit job will
  fail until upstream ships a fix, or someone decides to audit with `--omit=dev`: ask the user, don't
  silently weaken the gate.

#!/usr/bin/env python3
"""Regenerate Kiln's app icons (original artwork, no Minecraft imagery).

Draws a 1024px kiln-mouth glyph with Pillow, then runs `tauri icon` (installed as a dev
dependency in ui/) to produce every size, and deletes the unused mobile icon sets.

    pip install pillow          # if missing
    (cd ui && npm ci)           # installs the Tauri CLI
    python3 tools/regen_icons.py [--out DIR]

`--out` defaults to src-tauri/icons. The Rust build of src-tauri needs these files to exist.
"""
import pathlib
import shutil
import subprocess
import sys

from PIL import Image, ImageDraw

ROOT = pathlib.Path(__file__).resolve().parent.parent


def draw(path: pathlib.Path) -> None:
    size = 1024
    img = Image.new("RGBA", (size, size), (0, 0, 0, 0))
    d = ImageDraw.Draw(img)
    d.rounded_rectangle((64, 64, size - 64, size - 64), radius=220, fill=(24, 33, 31, 255))
    d.rounded_rectangle((232, 300, 792, 800), radius=60, fill=(40, 54, 50, 255))
    d.pieslice((232, 250, 792, 610), 180, 360, fill=(40, 54, 50, 255))
    d.pieslice((372, 430, 652, 710), 180, 360, fill=(95, 185, 154, 255))
    d.rectangle((372, 570, 652, 800), fill=(95, 185, 154, 255))
    d.rectangle((372, 740, 652, 800), fill=(24, 33, 31, 255))
    img.save(path)


def main() -> int:
    out = ROOT / "src-tauri" / "icons"
    if "--out" in sys.argv:
        out = pathlib.Path(sys.argv[sys.argv.index("--out") + 1]).resolve()
    source = ROOT / "icon-source.png"
    draw(source)
    try:
        subprocess.run(
            ["npx", "tauri", "icon", str(source), "-o", str(out)],
            cwd=ROOT / "ui",
            check=True,
            stdout=subprocess.DEVNULL,
        )
    finally:
        source.unlink(missing_ok=True)
    for mobile in ("android", "ios"):
        shutil.rmtree(out / mobile, ignore_errors=True)
    print(f"icons written to {out}: {len(list(out.iterdir()))} files")
    return 0


if __name__ == "__main__":
    sys.exit(main())
